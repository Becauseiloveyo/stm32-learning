# 衣架如何在电量有限、网络不稳时发送提醒

本包运行在电脑上。时间来自合成情景的整数秒时钟，能量单位为 J，所有结果标记为 `SYNTHETIC_UNCALIBRATED`，没有随机抽样。沿用 [P1 的事件与预测契约](T11-EVENT-CONTRACT.md)。衣架底部横杆中央接触得到确认、有有效的热与局部干燥证据时，才接纳用于衣物预测的观测。接触和热状态在这里由外部输入声明。

## 一次采集或发送会用多少电

| 项目 | 本轮采用的情景参数 | 计入电池账的方式 |
| --- | --- | --- |
| 可用电量 | 0.25 Ah × 3.7 V × 0.8 × 3600 = 2664 J | 主动动作保留 5%，即 133.2 J。静置背景仍会耗电 |
| 连续背景 | T12 的 0.2 mW | 负载功率 × 已过时间 ÷ 0.85 |
| 一次完整测量 | T05 的 30 s 基线、20 s 冲洗、90 s 恢复。全程 2 mW，冲洗另加 0.2 W，两个风门动作各 0.05 J | 动作本身为 4.38 ÷ 0.85 ≈ 5.15 J，另有同期连续背景。取消时结清已用能量，风门打开时支付关闭费用 |
| Wi-Fi | T05 的 0.6 W，成功占用 6 s，超时占用 20 s | 成功约 4.24 J，超时约 14.12 J，均另计背景。T12 的 8 s 无线脉冲不叠加 |
| 观测与唤醒 | 一个外部雨头样本或一个 M6 观测包按 0.02 J 负载侧预算，湿事件另加 0.005 J | 即时付费，同时保住在途动作预留。低电量时雨头读数变为未知，未取得的预测样本按缺测处理 |
| 人工充电 | 每段单独声明外接输入 W 与效率，按半开区间累计 | 先满足区间负载，再储存净盈余，溢出计弃充；边界的瞬时风门动作随后扣款。当前无太阳能供电输入 |

测量与无线互斥。开始前必须有足够的**当前电量**支持最坏全过程、同期背景和储备。此时只检查，随后才逐段扣电。无线时长把建链和一次小事务合在一起，未模拟字节吞吐或服务器的计算耗时。参数来自 [冻结的 T05、T12 接口](team/baseline-t11-p2/snapshot.json) 和本轮附加的雨头唤醒假设。电脑、服务和模拟接收端的耗电不计入衣架电池。

## 同一秒先处理什么

1. 结清刚过去的区间和到点的动作，推进证据到期。之后按输入序列处理这一秒已经到达的本地观测、换衣、插拔电等事件。
2. 湿证据会撤销旧预测。若测量正在进行，结清安全退出，再调度无线。受水优先仍受电量、在途无线与重试退避约束。接通充电时热状态变为受干扰，拔线后为未知，需要新的独立清除声明。
3. 无线已连续可用满 6 秒时处理上传，按实际已付费且匹配时间与安装位置的样本运行电脑侧 M6，保存当前状态并尝试模拟接收。缺失包以显式缺测送入 M6，上传时已过期的工作丢弃。完整测量的计时结束本身不会凭空产生传感器数据。
4. 再考虑启动新的无线，最后才考虑普通测量请求。普通积压每 60 秒检查一次。无线失败按 60、300、900、3600 秒退避，连续失败 5 次后本次运行停止尝试，成功确认可重置连续失败数。低电拒绝后至少过 60 秒重新检查。

## 断网与重启

端侧保留一份独立的最新状态，另有默认最多 32 条的历史队列。两者通过同一个 SQLite 事务写入。队列满时淘汰最早历史并累计淘汰数。每次发送都携带最新状态及最多一条待确认历史。服务保存迟到历史时，只有更新的版本才能改变当前展示。确认只释放相应设备、相应摘要的那条记录。

服务端按最新状态和原始有效期决定可见内容。模拟接收端持久记录已经提醒过的通知键。重新发送能更新显示，同一键只产生一次新提示。换衣发生在离线期间，远端可能继续显示上次同步且尚有效的状态。到期查询会隐藏它，重新连接后以新状态为准。

单纯重开消息库可以续传。若衣架本身重新启动，恢复入口先读取已提交序号，用新的启动标识写入一份接触、受水和预测均未知的状态，写完才允许上传。需要同一块持久存储、可信的单写者、单调逻辑时间和新启动标识。重启情景中电脑仍保存模拟电池账和退避时钟；设备更换存储、断电中的真实风门位置和电量恢复仍待研究。SQLite 事务复用 [T07 的实际存储代码](../research/notification_t07/storage.py)，P2 自己处理快照和确认包，未更改旧协议。

## 在本机复现

```sh
python -B -X utf8 -m research.integration_t11.p2.replay
python -B -X utf8 tools/check_integration_power_transport.py
python -B -X utf8 tools/check_integration_power_transport.py --check-receipt
```

第一条会重新运行九个情景并逐字节比较结果。[保存的轨迹](../research/integration_t11/p2/results/replay.json) 分列本地发现、排队、无线开始、服务保存和模拟接收的时间。情景生产端给定的受水起点只在事后评分时使用。所有情景的手机送达时间均为未知，收衣授权始终关闭。单个雨头润湿也无法区分雨、露水或喷溅。
