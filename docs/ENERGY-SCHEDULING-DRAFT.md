# 储能与测量调度预研草案

日期：2026-10-23。独立预研；不是 T05 主线验收，也不是电芯规格或整机续航结论。T04 尚未接入。实现及复现入口：[research/energy/README.md](../research/energy/README.md)，交付记录：[能源报告](team/reports/energy.md)。

## 1. 输入与可作出的结论

只使用冻结的 `docs/team/baseline-v1/analysis/energy_budget.py`、`docs/team/baseline-v1/power-notification-design.md`。生成时核对 `snapshot.json` 的 SHA-256，不导入正在变更的主模型。此处不沿用供电文档中的未来产品判干授权分支，遵守 PROJECT 的当前研究状态：未确认、没有收衣授权。

本原型回答：在给定负载、收能、初始储能和外部请求下，哪些预算服务有机会完成，哪些未完成，能量去了哪里。它不回答衣服何时干、测量是否有效、通知是否真的抵达手机。不得从固定与按需的能耗差推出相同判干准确率或实际节能收益。

参数唯一执行入口为 `research/energy/model.py::Config` 与 `scenarios.py`；输出的 `case-*/input.json` 保存全部数值。以下说明数值来源，不建立另一套可编辑配置。

| 参数类别 | 来源及含义 |
|---|---|
| 运行背景负载 | 冻结基线 1 mW，加原 4 mWh/日零星负载均摊到全天；处于运行状态才适用，不重复另加 misc |
| 测量动作增量能量 | 基线风机 0.2 W × 20 s，加气窗完整开关 0.1 J，即 4.1 J/周期；不含已经计入背景的部分 |
| 测量动作占用时间 | **本原型新增的 5 分钟占位假设**，既不是 T01 协议时长，也不表示物理上足够测量；低电量不缩短它，主线集成必须整体替换为协议完整时长与能量 |
| 联网 | 基线成功 0.6 W × 6 s；失败超时采用 0.6 W × 20 s 的假设；均占一个分钟格，按超时能量准入，实际成功才使用较小能量 |
| 储能与效率 | 基线 3.7 V × 1.5 Ah × 70% = 3.885 Wh 可用储能；负载侧到电池侧除以 0.85；不再次乘可用比例 |
| 新增低电量行为 | `stop/restart/low_enter/low_exit` 为 0.05/0.15/0.30/0.45 Wh，均是软件演示阈值；不是电压、SOC 标定值或硬件保护条件 |
| 新增停止／启动负载 | 停止时仍有负载侧等效 0.05 mW；重启额外 0.002 Wh。均未测；停止并不意味着零耗电 |
| 新增联网限制 | 每日 0.08 Wh 电池侧额度，最多 5 次尝试；失败结束后按 1/5/15/60 分钟退避，无随机抖动；预算跨模拟重启保留 |

基线的 30% 工程余量与向上取整是规划量，不作为虚构的实际耗散写入账本。要做余量压力情景，应显式增加具体负载或降低收能／容量，再生成新输入与输出。额外软件 stop 储备叠加在基线“70% 可用容量”之内，较保守；将来需避免实测截止、可用容量与软件储备重复扣除。

所有构造情景确定性生成，`seed=null`。仅边界随机检查使用固定种子 `20261023`，不是天气或衣物生成器。

## 2. 时序与能量账本

步长为 1 分钟；事件、截止、收能区间都使用非负整数分钟。区间为 `[start, end)`。先处理到达／过期，再用当前储能做启动检查，最后结算该分钟的收能与负载。**这一分钟尚未收到的太阳能不能让分钟起点的动作获准执行。**

只有一个动作通道，测量与联网不重叠。固定任务表每 10 分钟提供测量机会；正有动作时不补回错过的固定机会。按需任务表只在请求到达后安排测量。已有测量不能追溯满足开始之后才到达的请求。一个周期最多服务一个请求；不合并不同批次或协议的证据。相同时刻优先关键请求，其次请求到达顺序及 ID；固定测量机会优先于联网。

无主状态机时，外部请求只是审计用假设工作量，暂停期间到达的请求也可在尚未过期时保留。**这不证明睡眠／掉电设备能捕捉到那些触发事件或将其持久保存**；真正接入需明确事件来源和重启后失效规则。

以电池侧可用储能 `S`、当前分钟收能 `H`、负载侧实际服务量 `L`、效率 `η`、弃能 `C` 表示：

```text
S_end = S_start + H - L / η - C
L_requested = L_served + L_unmet
conversion_loss = L_served / η - L_served
0 <= S_end <= capacity
```

太阳能输入已经是收能损耗之后、进入系统／储能的电池侧能量，不能再乘充电效率。该分钟先满足背景和动作，剩余超过容量的部分计弃能；相当于允许同期太阳能供负载，未刻画电源路径开关波形。

启动动作必须已有：`完整动作最坏负载能量 / η + 动作整个占用时段背景能量 / η + stop储备`。检查不看未来阳光，联网检查也不看将来是否成功。仅在获准后，环境假设才决定该次联网的实际能量和结果。每分钟扣除动作能量的均匀份额，完整占用期结束且足额支付才记 `budget_completed`。网络失败仍支付能量，按限额重试，不能视为服务完成。

这是平均负载的时间序列模型：20 秒风机、气窗开关和 6/20 秒无线能量被摊到各自占用格中。低电量准入保守地预留全程能量，但一分钟内的峰值、压降、充电先后与保护动作均未模拟，不能当作瞬时供电验证。重启能量在一个分钟边界一次支付，其时长同样未建模。

账本与请求短缺分别记录，避免把“不执行”藏成成功：

| 字段 | 含义与使用限制 |
|---|---|
| `unmet_requested_load_wh` | 本分钟实际请求的背景／已启动动作的未供部分；进入需求守恒，但不进入已耗能量 |
| `unserved_jobs_reference_load_wh` | 每个未完成请求只计一次参考动作能量；测量用完整周期、联网用超时预算；用于表示待服务规模，不是电池消耗，也不是恢复服务所需能量的精确值 |
| `energy_blocked_jobs_reference_load_wh` | 上述请求中，曾被停止状态或能量不足阻止的子集；多个原因可能同时存在，不声称因果唯一 |
| `shed_background_reference_load_wh` | 停止模式相对正常背景减少的参考负载；不是实际能耗，不与前两项相加作物理守恒 |
| 请求 `status/block_reasons` | 到期、重试耗尽、低优先级搁置、日预算限制、时间不够、储能不足等；反复被阻止不会反复累加完整动作能量 |

动作正常结束且期限内才完成请求。没有足额启动预算时不启动，不支付不存在的动作，也不增加完成次数；后台不足则保留缺口，防御性中断分支不会产生成功。由于全额预留，正常配置下已准入动作不会在途中因能量不足而中断。

## 3. 低电量、迟滞与证据边界

`normal → low` 使用 low_enter，`low → normal` 必须达到更高的 low_exit。`running → stopped` 使用 stop，`stopped` 仅在达到更高 restart 且支付启动成本后退出。停止期间不进行测量或联网；低电量只搁置非关键摘要，关键测量仍须完整准入。初始储能高于 stop 时假设已经启动，不额外支付初始启动成本；恢复启动会收费。

所有请求始终带 `research_state=unconfirmed`、`collection_authorized=false`。原型没有判干阈值字段，也没有通过调节低电量门槛改变测量证据的路径。测量“预算完成”不等于质量有效、独立复核成功或可以收衣。Wi-Fi“预算完成”只对应输入网络环境下的一次假定确认，不是手机送达。

## 4. 对照情景与指标

五组情景的完整事件均落在 `results/case-*/input.json`，每组用同一请求、阳光、网络和初始储能分别运行 fixed/demand：

1. 正常两日：候选可用储能满电，日收能 0.30 Wh。
2. 七日无光：故意从仅剩 0.12 Wh 开始，暴露服务失败；不能当成满电连续七日续航测试。
3. 弱网两日：前 36 小时无确认，之后恢复；检查超时能量、退避、次数和日额度。
4. 恢复充电五日：从停止状态开始，两日无光，然后三日各 1.20 Wh 收能。
5. 迟滞六小时：先给六次小收能脉冲，后给较大脉冲，观察弱光期间是否反复重启。

两组日收能源自基线假设 `2 W × 等效日照小时 × 0.60`，在 10:00–16:00 均匀分布到电池侧。它不是实测阳台天气。细小脉冲是人为的边界压力输入。

外部测量请求约每 40 分钟一次、固定机会每 10 分钟一次，初始相位刻意错开。其他外部请求为小时摘要与约每日四次研究状态事件；末尾不足完整有效期的请求不生成，全部实际输入作为两策略共同分母。这里没有被动趋势检测器，没有真实干燥时刻；结果只说明这个人为请求稀疏度下的预算差异。被动监测假设包含在背景负载内，其真实成本和漏触发率未知。

同时报告实际负载、电池耗能、储能、弃能、未完成请求、未完成累计等待、仅成功样本的等待均值／P95、停止时长、重启次数，并按测量／联网分别给无结果比例。等待从外部请求到预算服务结束，不是从衣物干燥到手机提醒；无结果比例是**预算服务无结果**，真实测量质量与判干无结果比例仍未知。没有完成样本时分位数为 null，不写成零。

弱网案例的当前日额度在网络恢复前已经耗尽；恢复后当日仍不能发送。此结果提示以后需讨论关键事件预留额度、额度恢复方式和最大允许等待，但不能为了好看的结果在本轮偷偷追加额度。

## 5. 建议与 T04 约定的接口

这些是交接建议，不是已通过验收的正式协议：

| 方向 | 字段／事件 | 合同要求 |
|---|---|---|
| T04 → 调度 | `event_id, session_id, protocol_version, at_minute, deadline_minute, kind, reason, critical` | ID 唯一，单调时间，协议版本和批次明确；到期不能靠节能延长证据有效期；当前 `Request` 已保留这些字段 |
| 测量协议 → 调度 | 完整时长、最坏动作能量、可中断位置、关闭气窗／安全退出能量、有效时段与热静置约束 | 替换占位全局参数；不能通过缩短恢复过程达成电量预算；未来需逐协议能量配置 |
| 能源估计 → 调度 | 可用储能及不确定区间、允许电源峰值、充电受限、温度／故障状态 | 实物应以保守能量和瞬态约束共同准入；本轮只有理想已知储能 |
| 调度 → T04 | `admitted/deferred/expired/interrupted/budget_completed` 及原因、动作 ID、开始／结束时间、已耗能量 | 这些是资源状态；不能增加有效复核计数。T04 还需接收测量质量与结果才能决定证据状态 |
| T04 → 调度 | 新批次、状态版本失效、取消请求 | 正式实现要取消旧批次队列；本轮逐请求不合并，但未实现取消／恢复持久队列 |
| 通知模块 ↔ 调度 | 单次最坏能量／时间、是否值得重试、结果层级、有效期 | 实际网络失败才触发退避；服务器确认与手机可见分开；日预算不会因软件重启清零 |

当前 Python `simulate(Scenario, policy)` 读取完整场景是为了重放，选择动作只使用到达事件和当前储能；测试覆盖“改动未来事件／阳光／网络，不改变此前轨迹”。正式固件需要事件回调和持久化状态，不能直接把离线列表当在线驱动。

## 6. 有效范围与待解决项

- 时间域为整数分钟、有限正时长；功率／能量有限且非负、效率 `(0,1]`、储能不超过容量；低／停／恢复阈值有严格迟滞顺序；太阳能和网络区间须有序、不重叠；异常输入直接拒绝。
- 不含电芯电压、温度／老化随时间变化、保护电路、稳压峰值、充电限流与末期降流、自放电曲线、真实光伏 I–V、动态热扰动。停止背景只是等效负载假设。
- 不含真实测量协议、质量门槛、低功耗传感器触发可观测性、持久化闪存成本、设备重启后批次恢复、手机后台推送可靠性。收能为外部场景假设，不是预测器。
- 下一步应由协调者在 T04 验收之后，确认状态机及 T01 完整协议的接口，重新估计动作能量与时长，加入取消／过期／质量结果回放，然后再进入 T05 正式集成。真实参数校准与续航、峰值测试留待 H01；本轮无需采购。
